# Quick Task 261003-02: Detect and fix every error under smarthelp

## Goal

`smarthelp/` had a red build. Run each gate it declares, fix what it reports, and
fix the defects the gates cannot see. Nothing is added: every task here removes a
failure.

## Detection

Run all four gates the project declares, not a guess at which ones matter.

| Gate | Command | Reported |
|---|---|---|
| Types | `npm run typecheck` | 2 errors |
| Lint | `npm run lint` | 1 error |
| Tests | `npx vitest run` | 4 failures, 1 file |
| Build | `npm run build` | 1 blocker (found only after the types were green) |

The build blocker was invisible to the other three: `tsc` reads a 0-byte file
without complaint and ESLint has nothing to parse.

## Tasks

### 1. `lib/status.ts` — the transition table disagreed with the trigger

`TRANSITIONS` is the TypeScript copy of §8.2; `enforce_booking_transition()` in
0011 is the enforcement. The live parity test compares them pair by pair and found
two genuine disagreements:

- `paid -> cancelled` — the trigger allows it (§8.2 flattens `paid..accepted`),
  `TRANSITIONS` said no. The Route Handler would have refused a cancellation the
  database would have permitted, on the exact path §16's cancellation fee exists
  for.
- `assigned -> refund_pending` — `TRANSITIONS` allowed it, the trigger refuses it.
  An *offer* is not in §8.2's predecessor set for `refund_pending`.

The trigger is the enforcement and matches the specification, so the table was
corrected to match the trigger.

Two more defects in the same file, both visible only once the parity test ran:

- `present()` indexed `TRANSITIONS[status]` unconditionally, so the fallback in
  `statusPresentation()` — the one path that exists for an unrecognised status —
  threw `TypeError` instead of degrading. An unknown status is now neither
  terminal nor cancellable, which is the only safe answer to give a UI.
- `step` was a hand-written number per status, a second copy of `CUSTOMER_LADDER`
  that had already drifted: `searching`, `otp_verified` and `extension_requested`
  each carried a step the stepper has nowhere to draw. Steps are now derived from
  the ladder plus an explicit alias table, so `step !== null` is a property of
  being on the ladder or aliased onto it.

- **files:** `lib/status.ts`
- **verify:** `npx vitest run test/status.test.ts`
- **done:** the 18 × 18 parity probe reports zero mismatches against the live trigger

### 2. `test/status.test.ts` — three assertions were asserting the wrong thing

The four failures were not four bugs in the code; three were bugs in the tests.

- The ladder was checked for *adjacent legal moves*. `paid -> assigned` goes
  through `searching` and `arrived -> in_progress` through `otp_verified`, both
  deliberately off the ladder, so the assertion demanded a move §8.2 forbids. The
  ladder is a presentation order; what it owes the caller is reachability. Now
  checked as a path, in both directions, so the bar also cannot run backwards.
- The "off the ladder means a null step" assertion contradicted the file's own
  design, which maps `searching` onto `paid`'s step on purpose. Replaced with the
  invariant that is actually true, plus a check that every alias points at a step
  that is on the ladder.
- The parity probe compared `X -> X` against the trigger. The trigger returns
  early when `NEW.status is not distinct from OLD.status` — a reschedule, a fee
  and a note all update the row without moving it — so it *always* allows those
  18 pairs, and `canTransition` deliberately says false. 18 guaranteed false
  mismatches, reported alongside the 2 real ones. Skipped, with the reason.

- **files:** `test/status.test.ts`
- **verify:** `npx vitest run test/status.test.ts`
- **done:** 27 passing, including 306 real pairs against the live trigger

### 3. `lib/bookingServer.ts` — a type error that was also a design error

`update({ status, version: booking.version + 1 })` failed to typecheck because
`version` is not in the generated `bookings.Update`. Adding it would have been
wrong: `bump_booking_version()` is a BEFORE UPDATE trigger that owns the
increment, so writing it here double-bumps the row and makes the lock compare
against a number no caller ever read. The optimistic lock is `where id and
version`; that half stays.

Also: `new ApiHttpError('ILLEGAL_TRANSITION', 'Cannot transition from  to ')` —
a template string with its interpolations removed, so every illegal transition
answered "Cannot transition from  to ". Now names both states.

- **files:** `lib/bookingServer.ts`
- **verify:** `npm run typecheck`
- **done:** clean, and the refusal is a sentence a person can read

### 4. `app/api/bookings/[id]/review/route.ts` — wrong columns, no ownership

`ratings` has `overall` and `comment`, not `rating` and `review`, and both
`customer_id` and `professional_id` are `not null` with no default. The handler
supplied neither, so the insert could not have succeeded at runtime even if it
compiled — `validate_rating_booking()` compares both against the booking row
*before* it fills anything in, so they have to come from the booking and never
from the request body.

- **files:** `app/api/bookings/[id]/review/route.ts`
- **verify:** `npm run typecheck`
- **done:** compiles, sends `overall`/`comment`, sources identity from the booking

### 5. `components/catalogue` — handlers named like hooks

`useAddress` and `useMyLocation` are event handlers on the public-location
context, not hooks. The `use` prefix made `SavedAddressPicker` fail
`react-hooks/rules-of-hooks` by calling `useAddress` inside a select `onChange`.
The name was the defect; renamed to `selectAddress` and `locateMe`.

- **files:** `components/catalogue/PublicLocationContext.tsx`,
  `components/catalogue/SavedAddressPicker.tsx`, `components/catalogue/LocationChip.tsx`
- **verify:** `npm run lint`
- **done:** no ESLint warnings or errors

### 6. `app/api/bookings/[id]/route.ts` — a 0-byte file failing the build

Next.js generates a type file that imports from every route module; an empty one
is not a module and the build stops there. Implemented `GET /api/bookings/[id]`,
the counterpart to the list route, resolving the status presentation server-side
so the browser does not recompute a copy of the transition table.

- **files:** `app/api/bookings/[id]/route.ts`
- **verify:** `npm run build`
- **done:** build completes; `/api/bookings/[id]` listed as a dynamic route

### 7. Ownership was checked nowhere in the booking routes

Found while fixing task 4, and the most serious thing in the batch.

`bookings` has `bookings_select_own`, so RLS would answer "is this yours?"
correctly — and none of it applies, because every Route Handler reaches Postgres
through `createServerClient()` and the service role bypasses RLS entirely.
`invoice`, `cancel` and `review` each called `requireAuth()` and then acted on
whatever id arrived. Any signed-in session could read any booking's amounts or
cancel any booking by naming its id. `requireCapability`/`requireStaff`/`requireAdmin`
were also dead code, so nothing else was standing in the way.

Fixed once, centrally, in `getBookingForCaller()` — the function every one of
these routes already reaches for — rather than three times in three handlers where
the fourth route would forget it. Staff roles may read any booking; a
professional is not staff, because their own bookings are Phase 4's concern.

- **files:** `lib/bookingServer.ts`, `app/api/bookings/[id]/route.ts`,
  `app/api/bookings/[id]/invoice/route.ts`, `app/api/bookings/[id]/cancel/route.ts`,
  `app/api/bookings/[id]/review/route.ts`
- **verify:** `npm run typecheck`, `npm run lint`
- **done:** every route resolves through `getBookingForCaller`; no route reads a
  booking by bare id
