## What was wrong

Eight defects from the four gates. The order they were found in matters: the
build blocker was invisible to the other three, because `tsc` reads a 0-byte
route file without complaint and ESLint has nothing to parse.

1. **`TRANSITIONS` had drifted from the trigger that enforces it.** Two real
   disagreements, found by the live parity probe against
   `enforce_booking_transition()`: `paid -> cancelled` was refused by the
   TypeScript table and allowed by the database — on the exact path §16's
   cancellation fee exists for — and `assigned -> refund_pending` was the
   reverse. The trigger matches §8.2, so the table was corrected to match it.
2. **`statusPresentation()` threw instead of falling back.** `present()` indexed
   `TRANSITIONS[status]` unconditionally, so the fallback written for an
   unrecognised status — the raw-cast-from-JSON case it exists for — died on a
   `TypeError`.
3. **Three off-ladder states carried a step the stepper has nowhere to draw.**
   `step` was a hand-written number per status, a second copy of
   `CUSTOMER_LADDER` that had already drifted. Derived now, from the ladder plus
   an explicit alias table.
4. **Three test assertions were asserting the wrong invariants.** The ladder was
   checked for adjacent legal moves when it is a presentation order (two of its
   gaps go through states deliberately off the ladder). The off-ladder-means-null
   assertion contradicted the file's own step-mapping design. And the parity
   probe compared `X -> X` against a trigger that exempts no-ops by design, which
   manufactured 18 false mismatches and buried the 2 real ones.
5. **`version` was written in an update the trigger already owns.**
   `bump_booking_version()` increments it in a BEFORE UPDATE trigger; writing it
   as well would double-bump the row and make the optimistic lock compare against
   a number no caller ever read.
6. **An illegal transition answered `"Cannot transition from  to "`.** A template
   string with its interpolations stripped out.
7. **The review route could not have worked.** `ratings` has `overall` and
   `comment`, not `rating` and `review`, and both identity columns are `not null`
   with no default.
8. **`useAddress` is not a hook.** It is an event handler on the location
   context, and the `use` prefix made `SavedAddressPicker` fail
   `rules-of-hooks` for calling it inside an `onChange`. The name was the defect.
9. **`app/api/bookings/[id]/route.ts` was 0 bytes**, which Next.js reports as
   "not a module" and which nothing else in the toolchain objects to.

## The one the gates could not see

**No booking route checked whether the caller owned the booking.**

`bookings` has `bookings_select_own`, so RLS would answer "is this yours?"
correctly. None of it applied: every Route Handler reaches Postgres through
`createServerClient()`, and the service role bypasses RLS entirely.
`invoice`, `cancel` and `review` each called `requireAuth()` and then acted on
whatever id arrived in the path. Any signed-in session could read any booking's
amounts, or cancel any booking, by naming its id. `requireCapability`,
`requireStaff` and `requireAdmin` were dead code, so nothing else was standing in
the way either.

Fixed once in `getBookingForCaller()` — the function all three routes already
reached for — rather than three times in three handlers, where a fourth route
would forget it. The reasoning is recorded at the function: this is the same
argument 0011 makes for putting the state machine in Postgres instead of trusting
every future caller to remember.

## Left alone, deliberately

- **`POST /api/bookings/[id]/reschedule` cannot succeed.** It calls
  `transitionBooking(id, 'draft', …)`, and no status transitions *to* `draft` —
  so it answers 409 on every request, including a legal one. It is marked
  `// simplified` and Phase 2's booking services are still in progress; building
  reschedule properly is phase work, not an error fix.
- **`transitionBooking`'s `actor` and `note` are accepted and discarded.** 0011
  reads `app.transition_actor` and `app.transition_note` as transaction-local
  settings, and PostgREST cannot set those in the same transaction as the update.
  Closing this needs a small `security definer` helper in a migration, which is
  a schema change and not this task's to make. Carried forward in STATE.md.
- **`cancel` writes no `cancellation_reason_code`, `cancelled_at` or fee.** Same
  reasoning: incomplete Phase 2 work, already tracked.
- **`vercel.json` declares eight cron paths with no handlers.** Pre-existing,
  unrelated to this batch, already in STATE.md's known issues.
