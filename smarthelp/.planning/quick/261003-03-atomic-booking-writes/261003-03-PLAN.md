# Quick Task 261003-03: Atomic booking write paths, quote token, seed data, docs

## Goal

Finish the Phase 2 work that was left half-wired: make a booking's creation,
cancellation and status change single transactions, implement §7.2's `quoteToken`,
make the demo data reproducible, and bring `docs/` and the planning state back in
line with the code.

Written by hand: `gsd-sdk` fails to load in this environment (see STATE.md), so
this artifact does not come from the usual tooling.

## Why the write paths had to move into the database

Creating a booking was three PostgREST requests: the booking row, its
`booking_items`, then a status update to `payment_pending`. A failure between any
two left a booking that existed with a total and nothing behind it, or a booking
stuck at `draft` holding an item list the customer never agreed to. PostgREST
cannot put two requests in one transaction, so the transaction had to move into
Postgres.

## Tasks

### 1. Migration `0028` — three `security definer` functions

`create_booking`, `cancel_booking`, `transition_booking`. All revoked from
`public`/`anon`/`authenticated` and granted to `service_role` only, with
`set search_path = public`, matching `0024`'s convention.

Two decisions worth the argument:

- **The actor is a parameter, not `auth.uid()`.** The history trigger reads
  `coalesce(auth.uid(), …)`, and a service-role request has no `auth.uid()` — so
  every privileged write was attributed to `system`. Each function sets
  `app.transition_actor` / `app.transition_actor_role` with `set_config(…, true)`
  and then performs the writes that read them, in the same transaction.
- **A version mismatch returns `NULL`, it does not raise.** "Someone else already
  moved this" is an ordinary result of two devices. Raising would produce a 500 and
  a support ticket where the right answer is `409 STALE_VERSION` and a re-read.

### 2. The routes call the functions

`POST /api/bookings` calls `create_booking`; the cancel route calls
`cancel_booking`; `transitionBooking` calls `transition_booking`. The cancel route's
`notes` now goes into the history note rather than `bookings.cancellation_notes`,
a column nothing read.

### 3. §7.2's `quoteToken`

`lib/quoteToken.ts`. `base64url(payload).base64url(hmac)`, keyed with
`SUPABASE_SERVICE_ROLE_KEY` — the server already holds it and it never leaves the
server, so a separate `QUOTE_TOKEN_SECRET` would be one more value to provision for
no additional strength. Fifteen minutes, per §7.2.

The token is provenance, not a price lock: the create route re-runs `buildQuote`
and compares the fresh total whether or not a token was presented. A *missing*
token is accepted; an *invalid* one is a `VALIDATION_ERROR`. And a valid token must
**agree with the request** — booking type, coupon, item list and total — because
`expectedTotal` is optional, so a genuine token for one cart would otherwise
verify against a different cart submitted with nothing to compare.

### 4. Seed data, and three bugs in it

`supabase/seed.sql` now creates five deterministic bookings across the state
machine. Getting it to apply took three fixes, each found by running it in a
transaction that was rolled back: `cancellation_fee` was nullable in the CASE for
non-cancelled rows; `actor_role` needed an explicit `::user_role` cast; and the
actor role `'system'` is not in the enum — the valid values are `customer`,
`professional`, `admin`, `support`, `ops`, `super_admin`, so an assignment is
attributed to `ops`, which is what `write_audit` already does.

### 5. Two harness bugs, found by a flake that reran green

A run of `npm run test:db` failed five tests; the rerun passed. Rerunning is the
worst response to a flake, so it was investigated:

- One shared `pg` connection carries two minutes of sequential queries against a
  pooler that recycles idle connections. When the socket dropped, every
  *subsequent* test in the file failed with a transport error. `dbEnv.ts` now
  detects the dead socket and reconnects once — and retries transport errors only,
  because a `check_violation` is a real answer.
- `npm run test:db` listed its files explicitly, so a newly added DB test file was
  silently outside the gate.
