## The bug worth remembering

The quote token's canonical form signs each item as a positional triple so the
signature cannot depend on key order. Verification returned that triple unchanged,
so a caller's `item.serviceId` was `undefined` — invisible until the create route
began *comparing* claims against the request, at which point every valid token
failed to agree with itself and no booking could be created. The unit test
(`test/quoteToken.test.ts`, "reads back what it signed") found it in one run.

The lesson is the shape of the defect: a signature check passed on a payload that
was in the wrong shape to use. Verification that only answers "is this genuine?"
is not the same as verification that answers "is this what I can read?".

## Second bug, in the harness

A DB run failed five tests; the rerun passed. Treating that as noise would have
left a gate that fails at random — which is worse than no gate, because people
learn to re-run instead of read.

The cause was one `pg` connection carrying two minutes of sequential queries against
a pooler that recycles idle connections. When it dropped, every later test in the
file failed on a transport error and looked like a dozen unrelated booking bugs.
Fixed by detecting the dead socket and reconnecting once, with
`test/db.connection.test.ts` provoking the drop deliberately so the recovery is
asserted rather than assumed. It retries transport errors only — a
`check_violation` is a real answer and must never be retried.

`npm run test:db` also listed its files explicitly, so the new DB test file was
silently outside the gate. It is a filter now, and the files run sequentially:
three live-DB files in parallel against one remote link produced `fetch failed`
and 5-second timeouts that had nothing to do with the code under test.

## Notes for the next person

- `0028` deliberately does **not** re-price. `p_money` is inserted as given. The
  authority for a price is `buildQuote()`; the function's job is to write a set of
  numbers atomically, not to decide what they are.
- `RESCHEDULABLE_STATUSES` is one list in `lib/status.ts`, read by the route and by
  the detail page. Do not reintroduce a second copy in the UI; that is exactly how
  the "reschedule answers 409 on every request" bug happened.
- The demo database has 191 addresses on the demo customer. That is residue from
  earlier test runs against the shared project, not seed output — `db:verify`
  asserts exactly one *default* address and ignores the rest.
- No commit was made. The working tree carries substantial pre-existing changes
  from outside this phase, and separating these files from those is a decision for
  whoever owns the branch.
