# 261004-gh9 — Fix logged-in customer booking flow (address creation at checkout)

## Context

A signed-in customer clicks "Browse services" on `/customer` and lands on the public catalogue `/services` (intentional; do not change this link). After selecting a service, duration, and slot on `app/services/[slug]/page.tsx` (BookingPanel), they navigate to `/customer/checkout?service=...` and reach `CheckoutForm`. At checkout they cannot complete the booking because the UI requires a saved address and there is no way to create one.

## Root cause

Checkout requires `addressId` (CheckoutForm 63, 123, 171) and shows a warning with no control when missing (185–189). `SavedAddressPicker` returns `null` when the customer has zero saved addresses (78). There is no frontend UI to create an address and no wiring to select it after creation; the POST endpoint exists but is never called from the UI.

## Solution

Create a minimal address-creation UI (`AddressForm`) wired into checkout: when there are no address options and no `addressId`, render the add-address form instead of a dead-end. On successful create, call `selectAddress(newId)` from `usePublicLocation()` so `CheckoutForm.ready` becomes true without reload. Ensure the picker/form cooperate (emit `onCreated` or provide a simple reload hook) so the new address appears in the picker.

## Files to create/edit

- Create: `lib/addressClient.ts` — browser fetch wrappers (`fetchAddresses`, `createAddress`, `setDefaultAddress`), following the `lib/bookingClient.ts` / `lib/catalogueClient.ts` pattern exactly, with `authorizationHeader()` from `@/lib/sessionHeaders`.
- Create: `components/catalogue/AddressForm.tsx` (client) — the missing "add an address" control, built on `lib/addressClient.ts`.
- Edit: `components/catalogue/CheckoutForm.tsx` — render the form when the customer has no addresses; keep existing behaviour otherwise.
- Edit: `components/catalogue/SavedAddressPicker.tsx` — minimal change so a newly created address appears (lift the fetch into a shared hook or accept a refresh trigger).

## Test tooling constraint (verified — overrides the earlier draft)

`vitest.config.ts` sets `environment: 'node'` and `include: ['test/**/*.test.ts']`. There is **no** jsdom, no happy-dom, and no `@testing-library/*` in `node_modules` or in `package.json`. Component/render tests are therefore impossible without adding dependencies and editing the vitest config, which the constraints forbid.

So the test plan is transport-and-payload testing of a pure client module, which is exactly the pattern this codebase already uses — `test/bookingClient.test.ts` exists for precisely this class of bug ("489 tests, none of which imported the module that was broken"). All extracted logic that carries a bug risk must live in `lib/addressClient.ts` (or another pure module) so it is reachable from a `.test.ts` file. Do NOT try to render React components in tests.

## Implementation steps

### 1. Create `lib/addressClient.ts`
Follow `lib/bookingClient.ts` precisely: exported `AddressApiError`, typed return shapes, `authorizationHeader()` merged into every request, and a doc comment in the house voice explaining why the bearer header is mandatory (see `lib/sessionHeaders.ts`, which already names "the checkout address picker showed no saved addresses" as a past symptom of getting this wrong).

- `fetchAddresses()` — GET, returns `{ addresses, defaultAddressId }`.
- `createAddress(input)` — POST, returns the created address id.
- Shape the create payload from an explicit input type mirroring `validateAddressInput` (`lib/validation.ts:546`): required `line1`, `area`, `city`, `state`, `pincode`; optional `label`, `address_type`, `line2`, `landmark`, `access_notes`, `lat`/`lng` (both-or-neither), `is_default`. Never include `customer_id`.

Verification: `npx tsc --noEmit` clean; the module mirrors `bookingClient.ts` structure.

### 2. Create `components/catalogue/AddressForm.tsx`
- `'use client'`, imports `createAddress` from `@/lib/addressClient` and `selectAddress` from `./PublicLocationContext`.
- Fields matching `validateAddressInput`. Validate the required fields client-side so the server round-trip is not the first line of defence.
- On success call `selectAddress(newId)` so `CheckoutForm`'s `ready` becomes true without a reload, then notify the parent via `onCreated`.
- Surface server field errors (the API returns flat `fields`, per `CheckoutForm.tsx:161`).
- House voice comments, Tailwind, lucide-react icons, consistent with `SavedAddressPicker.tsx`.

Verification: typecheck clean; no rendering test (impossible — see constraint above).

### 3. Wire it into `CheckoutForm.tsx`
- `CheckoutForm` must know whether the customer has any addresses, because `SavedAddressPicker` renders `null` when the list is empty (line 78). Use `fetchAddresses()` from `lib/addressClient` rather than duplicating raw fetch logic.
- Render logic: `addressId` present → picker as today; no `addressId` but addresses exist → picker + existing amber notice; no addresses → `AddressForm` in place of the dead-end notice.
- After a successful create, the picker list must include the new address. Prefer a shared reload path over a `key`-remount hack, but a remount is acceptable if it is clean.

Verification: `addressId` set → confirm enabled (line 171); zero addresses → form rendered; existing customers unaffected.

### 4. Edit `SavedAddressPicker.tsx`
- Prefer routing its fetch through `lib/addressClient.ts` so both the picker and the form share one transport and the auth header has a single source. Keep the current three-state behaviour (renders nothing when signed out or when the list is empty) intact.

### 5. Tests — `test/addressClient.test.ts`
Model on `test/bookingClient.test.ts`: `vi.mock('@/lib/supabase')`, mock `global.fetch`, helper to read the last call.

Must cover:
- The bearer token reaches the wire on `createAddress` (the regression class that `bookingClient.test.ts` was written for).
- The POST body contains exactly the allowed fields and never `customer_id`.
- `lat`/`lng` both-or-neither handling.
- A non-ok response raises `AddressApiError` carrying the server's `fields`, so the form can map errors to inputs.
- A signed-out call (no token) still issues the request and lets the server's 401 through, rather than throwing client-side.

Verification: `npx vitest run test/addressClient.test.ts` passes; `npx vitest run` shows no regressions; `npm run lint` and `npm run typecheck` clean.
