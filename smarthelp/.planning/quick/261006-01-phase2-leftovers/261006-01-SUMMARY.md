## Task 1 — `bookingView()`: one answer where there were three

`app/api/bookings/[id]/route.ts` had drifted into duplicated joins (`booking_items`,
two different status-history reads, a service-role `from`s chain). It now calls
`bookingView(id, customerId, role)` from `lib/bookingServer.ts`, which awaits
`getBookingForCaller` first (so 401/403 come from the same place as everything
else), then loads items and history in parallel with `loadBookingItems()`, and
returns one 6-key payload:

- `booking` (the row, `item_counts` folded into it), `items`, `history`,
  `statusPresentation` (now a documented `known` shape), `eligibility` and
  `availability`.

`app/api/bookings/[id]/invoice/route.ts` shares the same `loadBookingItems()`
(items ordered `created_at` asc — the invoice already relies on that order, it
just no longer re-implements it). The route tests gained a key-set snapshot
(`routes.bookings.test.ts`, 40→41 tests) pinning the detail and invoice payload
shapes, so a future hand-rolled join that forgets an aggregate fails loudly.
`docs/API.md`'s detail-payload paragraph and both `docs/FEATURES.md` mentions
("no consolidated read model" — dropped) say the same thing the code does.

## Task 2 — the availability error code, and the trap it fed

The uncovered-locality gate in `app/api/availability/route.ts` threw a 409
`VALIDATION_ERROR` whose `details.reason` said `outside_coverage`. That was the
wrong code: nothing the caller sent was invalid — the *place* was. It now throws
`SERVICE_UNAVAILABLE` with no status override (422 via the table) and
`details: { location, reason: "outside_coverage" }`, which
`docs/FEATURES.md` §25.1 has described since Phase 1.

Three connected fixes landed with it:

- **`SlotPicker`** was branching on `error?.details?.reason` (which history has
  shown cannot be trusted) — it now branches on the documented
  `error?.code === 'SERVICE_UNAVAILABLE'` and *then* the reason.
- **`docs/API.md`**'s four edits line up: `VALIDATION_ERROR`'s override count
  (now "409 in one place"), `SERVICE_UNAVAILABLE`'s row (both an uncovered
  locality and a service not run there, distinguished by `details.reason`), the
  "Codes that disagree with their status" table (availability row removed), and
  the §5.3 blockquote that told clients to branch on `status === 422` instead of
  `code` — rewritten to say the two 422s share a code but differ by reason.
- **`savedAddressSelection.ts`** gained `shouldClearAddress()` (the Rule-2-style
  gap in 261004-gh9's still-open note): when the picker has *loaded* a list that
  contains none of the stale `addressId`, the selection is cleared. It is gated
  on `loaded`, not `settled`, so an empty result is treated as a fact while a
  failed fetch is left in place; `SavedAddressPicker` wires `clear()` and reports
  `loaded: options !== null`, and `BookingPanel`'s "Use a saved address"
  selection re-renders accordingly. 5 new tests pin the predicate
  (`savedAddressSelection.test.ts`, 15→20).

## Deviations from the plan

- **The `db:schema` gate cannot be read as `git diff --stat supabase/schema.sql`
  "only the comment lines from 0007".** This working tree carries large
  pre-existing uncommitted changes, and the *committed* `schema.sql` is from
  Phase 1 (`baf43bf`); the diff shows 1526 insertions that are entirely
  pre-existing Phase 2 drift (migrations 0011–0028). What this task contributed
  is exactly the 0007 comment lines, provable two ways: `git diff` on
  `0007_service_catalogue_seed.sql` is comment-only (9 lines), and the
  regeneration is **idempotent** (hash stable across re-runs), so the file on
  disk now equals what the migrations produce, no more and no less. The plan's
  own environment note forbade `git diff` as a gate everywhere else precisely
  because of this tree.
- **`requireCapability` and `isUuid` stayed** — the record listed them as dead
  code; the plan itself directed keeping wrongly-listed symbols and correcting
  the record, which is what happened. `parsePaging` stayed for the same
  plan-directed "tested-but-unwired" reason.
- **`docs/ARCHITECTURE.md`'s file tree still says "0000–0008, 0024–0027"** and
  the 273/243/30 suite counts remain in `ARCHITECTURE.md`, `DATABASE.md` and
  `SETUP.md`. The plan explicitly put these out of scope ("note it in
  `STATE.md`; do not expand this plan"), and `STATE.md` records them under "Also
  not fixed, and deliberately out of scope".
- **No commit.** A quick task by decree, and the `done` criteria say so
  explicitly; `STATE.md`'s Quick Tasks Completed record and the git history stay
  exactly as they were found.
